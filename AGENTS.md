# CLAUDE.md

## Технический стек
- Unity 6000 LTS (или новее)
- C# 9.0+ (целевая версия .NET в Unity)
- 3D графика, URP (MeshRenderer, 3D коллайдеры и физика)
- TextMeshPro для UI
- UniTask для всего растянутого во времени

## Подсистемы на флаге

Выключаются компонентом, а не удалением (см. «Консервация вместо удаления» в
[CodeDocs/Architecture.md](CodeDocs/Architecture.md)):

- `PartGrabber` — выключён, детали не берутся; сцена и данные остаются целыми.
- `HotbarView` — выключен, ячеек внизу экрана нет; сам инвентарь (Q и колесо) работает.
- `BoardStatusView` — необязателен; без него вердикт уходит только в консоль.
- `FirstPersonPlayer` — выключён, игрок стоит на месте; комната и камера целы.
- `captureCursor` у `FirstPersonPlayer` — снят, курсор свободен, обзор мышью не идёт.
- `CrosshairView` — выключен, прицела в центре экрана нет.
- `ComputerTerminal` — выключен, компьютер в комнате стоит, но не включается.
- `PhotoCamera` — выключена, фото публикуется кнопкой терминала по всей витрине, а не
  по кадру, и фотоальбома в компьютере нет.
- `useInventory` у `EconomyConfig` — снят, на поднос выкладывается весь каталог, как до
  коробок; склад и цены при этом остаются целыми.
- `crouchIsToggle` у `PlayerConfig` — присед переключателем вместо удержания.
- `dropOnRelease` у `InteractionConfig` — снят, отпущенная деталь возвращается на
  поднос вместо падения там, где её отпустили.
- `buildProps`, `buildCeiling`, `buildLamp`, `buildComputer` у `RoomConfig` — мебель,
  перекрытие, лампа и компьютер.

Прототип этапа 1 описан в [CodeDocs/Prototype.Stage1.md](CodeDocs/Prototype.Stage1.md),
игрок от первого лица и серая комната — в [CodeDocs/FirstPerson.md](CodeDocs/FirstPerson.md),
игровой цикл с коробками и фото — в [CodeDocs/Economy.md](CodeDocs/Economy.md).

## Архитектура

Подробно, с причинами и примерами — [CodeDocs/Architecture.md](CodeDocs/Architecture.md).

### Обязательно в любой игре
- **Логика — в чистом C#.** Правила, состояние и расчёты живут в обычных классах без
  `MonoBehaviour`. На MonoBehaviour — только ввод, отображение, анимация и жизненный цикл.
  Проверка: логику можно прогнать в тесте без сцены и без единого кадра.
- **Время — `async UniTask` с `CancellationToken`, не корутины.** Токен берётся у
  объекта-владельца (`destroyCancellationToken`), `OperationCanceledException` глушится
  только в точке запуска, то, что должно уцелеть при отмене, — в `try/finally`.
- **Синглтоны — только для сервисов движка** (`AudioManager`, `SaveManager`, `Lang`).
  Игровые правила получают зависимости при создании, а не через `Instance`.
- Базовые абстрактные/generic-классы для общей логики, конкретика — в наследнике
  (`AudioManager<TId>`, `SaveManager<TData>`).

### Когда появляется пошаговая логика, ИИ или много систем — рекомендуется
- Три слоя: `Scripts/Data` (конфиги, логики нет), `Scripts/Core` (чистый C#, вся логика),
  `Scripts/Unity` (MonoBehaviour, не знают ни данных, ни логики).
- Вызовы из ядра в сцену — через порты: интерфейсы в одном файле, методы-инструкции
  («встань здесь»), ни один не возвращает решение.
- Один загрузчик держит корневой конфиг и явно, в коде, собирает ядро — не порядком `Awake`.
- Корневой конфиг — хаб ссылок на маленькие конфиги; все клавиши — в одном ассете.

### Всегда
- Необязательный префаб эффекта: пусто — рантайм рисует примитив. Арт не блокирует механику.
- Ненужная подсистема выключается флагом, а не удаляется; такой островок назвать в этом файле.

## Стиль кода C#

### Общие правила
- Современный C#: expression-bodied методы, `var` где тип очевиден, null-условные операторы (`?.`, `??=`).
- Никаких `FindObjectOfType` или `GetComponent` в Update — кешировать в Awake/Start.
- Для состояния — `[SerializeField] private` или `[field: SerializeField]` с автосвойствами. Публичные поля только для ссылок на префабы/объекты.
- Для методов, вызываемых из UI — префикс `On` (`OnPlayButton`).
- Имена: методы PascalCase, локальные переменные camelCase, константы UPPER_CASE.

### MonoBehaviour
```csharp
// Хорошо
public class SomeComponent : MonoBehaviour
{
    [SerializeField] private int someValue = 5;
    
    private void Start() => CacheComponents();
}
```

### Синглтон (только сервисы движка)
```csharp
public class SomeManager : MonoBehaviour
{
    public static SomeManager Instance { get; private set; }
    
    private void Awake()
    {
        if (Instance != null) { Destroy(gameObject); return; }
        Instance = this;
    }
}
```

### События
```csharp
// Статические события
public static event Action<Vector3, int> OnSomethingHappened;

// Вызов
OnSomethingHappened?.Invoke(position, value);

// Подписка с отпиской
private void OnEnable() => ClassName.OnSomethingHappened += Handler;
private void OnDisable() => ClassName.OnSomethingHappened -= Handler;
```

### Оптимизация
- `NonAlloc` версии физических запросов где возможно.
- `sqrMagnitude` вместо `Vector3.Distance`.
- `GameObject.FindWithTag` допустим, `GameObject.Find` — нет.

### Именование
- Классы: существительное, без префиксов.
- Методы: глагол + объект.
- События: `On<Действие>`.
- Префабы: точное имя класса.

### Запрещено
- `GameObject.Find`.
- Строки для тегов/слоёв в коде — константы или `[SerializeField]`.
- Магические числа — в константы или `[SerializeField]`.
- `Debug.Log` в Update.
- `Time.timeScale = 0` без возможности восстановления.
- Корутины (`IEnumerator`, `StartCoroutine`) в новом коде — вместо них UniTask.
- `GetComponent<T>() ?? AddComponent<T>()` — отсутствующий компонент приходит из движка
  не настоящим null, `??` его не ловит, и падает уже следующая строка. Только
  `TryGetComponent`.

## Общие правила

### Делает модель (пишет код)
- Скрипты MonoBehaviour.
- Editor-скрипты (создание тегов, слоёв, валидация, пакетная обработка).
- Генерация констант для тегов, сцен, слоёв.
- ScriptableObject и конфиги.
- Assembly Definition файлы.
- .gitignore и другие dot-файлы.

### Делает разработчик (руки в редакторе) - описать при необходимости
- Создание сцен, добавление в Build Settings.
- Создание Canvas, размещение UI-элементов.
- Создание префабов (drag в папку).
- Настройка SpriteRenderer (цвет, размер, спрайт).
- Добавление и настройка коллайдеров, Rigidbody.
- Назначение тегов и слоёв через Inspector.
- Перетаскивание ссылок в поля скриптов.
- Привязка методов к кнопкам (onClick).
- Пространственное размещение объектов на сцене.

## Работа в редакторе через MCP Unity

Если запрос пользователя начинается с префикса **`mcpunity`** (в любом регистре,
с пробелом или двоеточием после), это явное разрешение работать в открытом
Unity Editor через MCP-сервер `mcp__unity__*` (плагин MCP for Unity), если он
подключён в текущей сессии.

В таком режиме допускается выполнять то, что обычно «руки в редакторе»:

- Создавать/удалять/переименовывать GameObject на сцене.
- Изменять компоненты, перетаскивать ссылки в поля скриптов.
- Привязывать `onClick`, тэги, слои, размеры RectTransform.
- Создавать/править префабы, добавлять компоненты.
- Запускать/останавливать Play Mode, открывать сцены, читать консоль.
- Прогонять тесты Editor/PlayMode.

Правила:
- Если префикс `mcpunity` есть, **но MCP for Unity не подключён** в этой сессии
  (нет инструментов `mcp__unity__*` в списке доступных) — честно сказать об
  этом и предложить альтернативу (правки в `.unity`/`.prefab` файлах вручную или
  инструкция «руки в редакторе»).
- Если префикса нет — действуем по умолчанию: правим только файлы проекта,
  редактор не трогаем, для сценовых правок выдаём инструкцию разработчику.
- Перед деструктивными операциями (удаление объектов, перезапись префабов,
  выход из Play Mode без сохранения) — кратко подтверждать намерение в ответе.
- После сценовых правок через MCP кратко перечислять, что именно изменилось,
  чтобы пользователь мог это увидеть в Hierarchy/Inspector.

Пример: `mcpunity добавь в сцену GameObject WindowManager и пропиши в него все
существующие UIWindow-окна` → работаем напрямую в редакторе, без инструкций
«перетащи это сюда».
