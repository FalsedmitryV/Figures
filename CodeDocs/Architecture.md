# Принцип архитектуры

Как писать игровой код, чтобы логика не срасталась со сценой, а общие модули можно было
вынести в `Stable`. Выведено на WishWorld (изометрическая пошаговая тактика), но от игры
не зависит.

Две ступени: **минимум** обязателен в любой игре, от пятнашек до тактики; **полная схема**
включается, когда в игре появляется пошаговая логика, ИИ или много взаимодействующих
систем.

## Обязательный минимум

### Логика — в чистом C#

Правила, состояние и расчёты живут в обычных классах, не в `MonoBehaviour`. На
`MonoBehaviour` остаётся то, что без движка не сделать: ввод, отображение, анимация,
жизненный цикл объекта.

```csharp
// Core: правило, ни одного MonoBehaviour
public class SlidingPuzzle
{
    public bool TryMove(Vector2Int cell) { /* ... */ }
    public bool IsSolved { get; }
}

// Unity: держит модель, передаёт ввод, рисует результат
public class BoardView : MonoBehaviour
{
    private SlidingPuzzle _puzzle;
    public void OnCellClicked(Vector2Int cell) { if (_puzzle.TryMove(cell)) Redraw(); }
}
```

Типы вроде `Vector2Int` и `Mathf` в логике допустимы. Недопустимы сцена, компоненты,
`Transform`, корутины.

Проверка: **логику можно прогнать в тесте без сцены, без префабов и без единого кадра**.
Если для этого нужен MonoBehaviour — граница нарушена. Отдельная папка `Core` при этом
не главное; главное — что в ней нет `MonoBehaviour`.

### Время — UniTask, а не корутины

Всё растянутое во времени — `async UniTask` с `CancellationToken`:

- корутине нужен живой MonoBehaviour-хозяин, то есть кусок движка внутри логики, которая
  объявлена чистым C#;
- отмена корутины — хендл, который надо где-то хранить; отмена токеном сворачивает всё
  дерево вызовов разом, включая то, что в полёте.

Токен берётся у объекта, который владеет процессом (`destroyCancellationToken` у
MonoBehaviour), и передаётся вниз. `OperationCanceledException` глушится только в точке
запуска: уровень, снесённый посреди действия, — обычное событие, а не сбой. Всё, что должно
уцелеть при отмене (флаги, блокировки ввода), пишется в `try/finally`, а не с надеждой, что
до конца метода дойдут.

```csharp
private void Start() => RunLevel().Forget();

private async UniTaskVoid RunLevel()
{
    try { await _level.Run(destroyCancellationToken); }
    catch (OperationCanceledException) { }
}
```

### Синглтоны — только для сервисов движка

`AudioManager`, `SaveManager`, `Lang` — сервисы уровня приложения, у них один экземпляр
по природе, и `Instance` им подходит. Игровые правила синглтонами не делаются: они
получают зависимости при создании.

## Полная схема — когда игра растёт

Рекомендация, а не требование. Окупается, когда логика становится многошаговой (ходы,
ИИ, способности) и её правят чаще, чем картинку.

### Три слоя

| слой | что лежит | что знает |
|---|---|---|
| `Data` | ScriptableObject-конфиги, структуры чисел | ничего. Логики нет вообще |
| `Core` | обычный C#, вся логика | знает `Data` и типы вроде `Vector2Int`/`Mathf`. Сцену — нет |
| `Unity` | MonoBehaviour | не знает ни `Data`, ни `Core`. Только выполняет инструкции |

### Порт: инструкция без вопроса

Все вызовы из `Core` в сцену собраны в один файл интерфейсов (в WishWorld —
`Core/ViewPorts.cs`). Каждый метод там — повелительное наклонение: «встань здесь»,
«проиграй смерть», «нарисуй маршрут». Ни один не возвращает решение.

Как только у вида спрашивают что-то в ответ, ему нужно мнение — а мнение это правило,
сбежавшее из слоя, который правилами владеет. Дальше правила живут в двух местах и
расходятся.

Интерфейсы лежат рядом друг с другом, а не возле своих реализаций, именно затем, чтобы шов
можно было прочитать целиком и увидеть, что он всё ещё узкий.

### Один загрузчик и явный порядок сборки

Ссылка на корневой конфиг есть ровно у одного Unity-класса — загрузчика (`GameBootstrap`).
Он строит ядро и отдаёт ему реализации портов и токен жизни. Всё остальное получает
значения вызовом, а не тянет их из ассета само.

Порядок создания сервисов написан в коде, а не отдан Unity: `Awake` между объектами не
упорядочен, и сервис, разрешённый из того синглтона, который успел создаться первым, —
классический баг «уровень остался без очереди ходов».

Проверка, что правило держится: ни у одного класса в `Unity/`, кроме загрузчика, нет поля
с типом из `Data`.

### Конфиг — хаб ссылок

Корневой конфиг не толстый файл, а набор ссылок на маленькие (`WorldConfig`,
`RulesConfig`, `PlayerConfig`, `InputConfig`…). Дизайнер, правящий ростер, и тот, кто
крутит камеру, не редактируют один ассет; вариант сборки — второй корневой конфиг,
меняющий пару ссылок.

Все привязки клавиш — в одном ассете: их надо проверять друг против друга. Коллизия, при
которой два действия сидят на одной клавише, невидима, пока поля разнесены по компонентам.
Ввод доходит до логики сырым кадром клавиш: что значит клавиша, решает логика, а не движок.

## Приёмы на любой масштаб

### Заглушка вместо предусловия

Эффект, снаряд, вспышка — с необязательным префабом: пусто, значит рантайм собирает примитив
в цвете. Механика становится играбельной в тот момент, когда появились её числа, а арт
превращается в улучшение, а не в условие старта. Та же идея у `RewardedAds`: без модуля
рекламы награда выдаётся сразу.

### Консервация вместо удаления

Ненужная сейчас подсистема выключается флагом и остаётся целой, а не вырезается. Удалённая
подсистема возвращается переписыванием; выключенная — снятием флага. В README / AGENTS.md
такой островок должен быть назван явно, иначе его начнут «чинить».

## Как этим пользоваться при выносе модуля

1. Найти в игровом классе места, где он спрашивает сцену, и заменить их на порт.
2. Вынуть из него игровые типы в дженерик-параметр или в конфиг (`AudioManager<TId>`,
   `SaveManager<TData>` — ровно этот приём).
3. То, что осталось знать про игру, оставить в наследнике в игре; в `Stable` уезжает ядро.
